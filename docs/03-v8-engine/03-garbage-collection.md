# 03-03 V8 垃圾回收（Orinoco）

> 对应 07-01 的应用层视角。本章从 V8 引擎内部拆解分代 GC：Scavenge、Mark-Sweep、Mark-Compact，以及并发/并行/增量标记如何降低停顿。

---

## 1. 分代假说

V8 基于"弱代假说"：大多数对象在年轻时死亡。因此按年龄分代，对年轻对象用快而频繁的回收，对老对象用 infrequent 但彻底的回收。

```
新生代 (Young)              老生代 (Old)
  From-Space ─┐           ┌─────────────┐
  To-Space   ─┘           │  长期存活    │
   复制算法                  │  Mark-Sweep │
   存活≥2次 → 晋升 ──────▶  │  Mark-Compact│
```

---

## 2. 新生代：Scavenge（复制）

（回顾 07-01）

- 新对象分配到 From-Space。
- 满时：标记存活 → 复制到 To-Space → 交换角色。
- **只处理存活对象**（通常很少），因此极快。
- 存活超过 `tenure` 阈值（默认 2 次）晋升老生代。
- 代价：始终浪费一半空间（双 space）。

---

## 3. 老生代：Mark-Sweep + Mark-Compact

（回顾 07-01）

1. **Mark**：从 GC Roots（全局、调用栈、闭包）遍历标记可达对象。
2. **Sweep**：回收未标记对象，产生碎片。
3. **Compact**：把存活对象移到连续空间消除碎片（成本高，仅在碎片影响分配时做）。

### Orinoco 优化
| 技术 | 作用 |
|------|------|
| 并行标记 | 多核同时标记，缩短 STW |
| 并发标记 | JS 运行时后台标记，不暂停 |
| 增量标记 | 标记拆小步穿插执行，降单次停顿 |
| 懒清理 | Sweep 推迟到需要内存时 |

---

## 4. 写屏障（Write Barrier）

晋升/并发标记需要追踪"老生代对象指向新生代对象"的引用（否则回收新生代时会漏标）。V8 用**写屏障**：每次写对象属性时插入检查，维护"老→新"引用集（remember set），保证 GC 正确性。

---

## 5. GC 停顿与 Node 影响

- 老生代 GC 仍有 STW（并发标记期间对象变更需重新标记）。大堆（如 4GB）的标记可能达 **几十 ms**。
- 表现为**偶发延迟尖刺**（07-01、05-11 提到用 `monitorEventLoopDelay` 观测）。
- 调优：`--max-old-space-size` 调上限；根因是修泄漏。

## 7. 本章总结

- 分代基于弱代假说；新生代 Scavenge 复制（快、费空间），老生代 Mark-Sweep/Compact。
- Orinoco 用并行/并发/增量标记 + 写屏障降低停顿。
- 大堆 GC 仍有 STW 尖刺，需用 `--trace-gc` 与 `monitorEventLoopDelay` 诊断。
- 根因优化是找泄漏，而非调大上限。

## 8. 思考题

1. 为什么新生代用复制算法而非标记-清除？什么情况下复制算法会变慢？
2. 并发标记时 JS 仍在运行，V8 如何保证标记结果正确？（提示：写屏障）
3. 如果一个对象"活了很久但很小"，它一直留在老生代会不会有问题？这启发我们什么编码习惯？
