# 03-02 V8 JIT 编译管线：Ignition → Sparkplug → Maglev → TurboFan

> 本章目标：理解 V8 如何把 JS 从源码变成高效机器码——分层 JIT 的设计哲学、各层编译器职责，以及"去优化（deopt）"为何重要。

---

## 1. 为什么需要 JIT

纯解释器（逐行执行字节码）慢；纯 AOT（提前全量优化编译）启动慢且难以应对 JS 的动态类型。V8 用**分层 JIT（tiered compilation）**：先用快但慢的编译让程序立刻跑，再对热点函数逐步升级到激进优化编译器。

---

## 2. 四层管线

```
JS 源码
   │
   ▼
┌─────────────────────────────────────────────┐
│ 1. Parser → AST → Bytecode (Ignition)        │  解释器 + 字节码
│    首次执行就生成，启动极快                    │
└─────────────────────────────────────────────┘
   │ 函数变热（调用次数 / 类型稳定）
   ▼
┌─────────────────────────────────────────────┐
│ 2. Sparkplug                                │  基线编译器（快速 JIT）
│    把字节码直译成机器码，不做优化，速度快     │
└─────────────────────────────────────────────┘
   │ 更热
   ▼
┌─────────────────────────────────────────────┐
│ 3. Maglev                                   │  中间件（V8 新层）
│    中等优化，比 Sparkplug 快、比 TurboFan 省  │
└─────────────────────────────────────────────┘
   │ 最热 + 类型高度稳定
   ▼
┌─────────────────────────────────────────────┐
│ 4. TurboFan                                 │  优化编译器（Speculative）
│    激进优化（内联、类型特化、逃逸分析）        │
└─────────────────────────────────────────────┘
```

> 注意：并非所有函数都会走完四层。多数冷函数停在 Ignition/Sparkplug；只有真正的热点才会被 TurboFan 优化。

---

## 3. 各层职责详解

### 3.1 Ignition（解释器 + 字节码）
- 把 AST 编译成**字节码（Bytecode）**而非直接机器码。
- 带**寄存器式解释器**，执行字节码。
- 收集**类型反馈（Type Feedback）**：记录函数参数类型、属性访问形状等。
- 启动最快（无需等待编译），但执行最慢。

### 3.2 Sparkplug（基线 JIT）
- 把 **Ignition 字节码直接翻译成机器码**，几乎不做优化。
- 速度快（编译成本低），生成的代码质量中等。
- 保留与字节码的映射，便于去优化时回退。

### 3.3 Maglev（中间件 JIT，较新）
- 位于 Sparkplug 与 TurboFan 之间，做**中等强度优化**。
- 比 Sparkplug 生成的代码更快，比 TurboFan 编译更快。
- 用于那些"热但还没热到值得 TurboFan"的函数，提升整体平滑度。

### 3.4 TurboFan（优化编译器）
- 基于 **Sea-of-Nodes IR** 与**类型反馈**做激进优化：
  - **类型特化**：假设参数一直是 `Number`，生成直接操作整数的机器码。
  - **内联（Inlining）**：把小函数体直接嵌入调用点。
  - **逃逸分析**：栈上分配、消除冗余。
  - **死代码消除、循环优化**等。
- 生成的机器码最快，但编译成本高、假设多。

---

## 4. 去优化（Deoptimization）

TurboFan 的优化是**推测性（speculative）**的：它假设"这个函数一直收到 `Number` 参数"。若某次调用突然传入 `String`：

```
优化代码假设 x: Number
   │
   ▼
实际调用 f("hello")  → 假设被打破
   │
   ▼
触发 Deopt  → 丢弃 TurboFan 机器码
   │
   ▼
回退到 Sparkplug / Ignition 字节码重新执行
   │
   ▼
V8 重新收集类型反馈，可能再优化
```

去优化的代价：那次调用会变慢（要回退重执行）。**频繁 deopt 是性能杀手**——通常源于类型不稳定（如数组内混装不同类型、对象形状频繁变化）。

---

## 5. 对 Node 开发者的启示

1. **保持类型稳定**：函数参数、数组元素尽量保持同一类型，利于 TurboFan 优化。
   ```js
   // 好：同类型
   function sum(arr) { let s=0; for(const n of arr) s+=n; return s; }
   // 坏：数组混装 number 与 string，触发 deopt
   ```
2. **隐藏类（Hidden Class）稳定**：对象属性增删顺序一致，V8 能复用隐藏类，属性访问变快。
   ```js
   // 好：固定形状
   const a = {x:1, y:2};   // 所有同类对象同形状
   // 坏：动态增删属性导致形状分裂
   ```
3. **监控优化**：`--trace-opt` / `--trace-deopt` / `--trace-turbo` 观察优化与去优化。

---

## 6. 可运行验证

```bash
node --trace-opt -e "function f(a,b){return a+b} for(let i=0;i<1e6;i++) f(i,i)" 2>&1 | head
# 显示 f 被优化（optimization id, reason: hot）

node --trace-deopt -e "
function f(x){return x+1}
for(let i=0;i<1e5;i++) f(i);
f('a');   // 触发类型变化 → deopt
" 2>&1 | head
# 显示 deopt 记录与栈
```

---

## 7. 本章总结

- V8 用分层 JIT：Ignition（字节码，快启动）→ Sparkplug（基线 JIT）→ Maglev（中等）→ TurboFan（激进优化）。
- 优化是推测性的，依赖类型反馈；类型突变触发去优化（Deopt），回退重执行。
- 保持类型/形状稳定利于优化；频繁 deopt 损害性能。
- Node 开发者可用 `--trace-opt`/`--trace-deopt` 诊断热点与去优化。
